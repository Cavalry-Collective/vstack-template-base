Keystone · design foundations

Many apps.
One design philosophy.

Keystone is the design foundation for every product prototyped from this template: the principles, tokens, and rules that make ten different apps feel like one practice built them. It is deliberately foundations-only — components stay flexible per app, but everything they're made of starts here.

Token-driven Light & dark WCAG 2.1 AA Reduced-motion safe Foundations, not components

How to use this guide

  • Starting a project? Rebrand the primitive tier of tokens.css (ramps, type scale, radius); this whole page re-derives. Review it in a browser — light and dark — and sign off before any screen is built. That confirmation is the visual keystone gate (apps/frontend/CLAUDE.md → Design guide).
  • Building a screen? Consume semantic tokens only. If a design needs a value the system doesn't have, extend the system — never the screen.
  • Reviewing? Every chapter below ends in checkable rules. A screen that violates one is the defect, whoever (or whatever) built it.
There are no special cases.

Use the established scale. No, really — use the established scale. If a real need isn't covered, either extend an existing token so the change lands everywhere at once, or add a new step to the canon here. A one-off value on one screen is how a design system dies.

Getting started

Design principles

Six commitments, in priority order. When two collide, the earlier one wins.

01

Clarity first

Strip away everything non-essential. Hierarchy, not decoration, does the explaining — a user should know where they are, what matters, and what to do next without reading twice. Reducing cognitive load beats delighting the eye.

02

No special cases

Every colour, size, space, radius, shadow, and duration resolves to a token. When the system can't express a need, extend the system — the scale grows once, screens never fork. Consistency is an architecture, not a discipline.

03

One primary action

Each view has exactly one filled, accent-coloured action; everything else is secondary or tertiary. Accent surfaces are rationed so the action that matters is always the most prominent thing on screen.

04

Every state is designed

Loading, error, empty, and success are first-class screens, not afterthoughts. Empty states explain and offer the next step; errors say what happened and what to do; feedback appears on the control that caused the work.

05

Accessible by default

AA contrast is a constraint on the token set, keyboard operability is assumed, focus is always visible, meaning never rides on colour alone, and reduced motion is honoured at the token layer. Accessibility is a floor, not a feature.

06

Calm surface, instant feedback

Interfaces stay quiet — motion is short, purposeful, and banded by surface size — but every interaction answers immediately. Perceived speed is part of the design: skeletons match layouts, and slow work never blocks acknowledgement.

Getting started

Using the tokens

One source, three tiers. The tiers are what make the system rebrandable, themeable, and impossible to fork by accident.

TierHoldsExampleWho touches it
1 · PrimitiveRaw, context-free scales: colour ramps, type sizes, space steps, durations--blue-400, --space-4Rebrand edits only this tier
2 · SemanticRole-named decisions pointing at primitives; the light/dark remap lives here--color-accent, --gutter-screenWhat components consume — these and nothing deeper
3 · ComponentPer-component overrides, only where genuinely needed--control-height, --control-radiusAdded sparingly as components stabilise
  • Dark mode is a semantic remap, never a primitive change — the same ramps serve both schemes; only the role assignments swap.
  • Pages and components never reach past a semantic token to a raw primitive or a literal value. A hex code or px literal in a screen is the greppable violation.
  • The app's token file is seeded from this one (src/tokens.<ext>); a committed token value must match its documented scale.

Foundation

Colour

A neutral ramp for structure, one accent for action, four intents for meaning, one highlight for what's new. Hover a step for its current value.

Primitive ramps

Steps run light → dark. In light mode: 50 = subtle background, 200 = border, 400–600 = content and interactive colour. Dark mode inverts the roles, not the ramps.

Semantic roles — what to actually use

TokenValueUse for
The intent formula.

Every intent (success, warning, danger, info, highlight) is one family applied three ways: subtle background = step 50 · border = step 200 · content = step 400–600 (light mode). Adding a new intent means adding a family and applying the formula — not inventing new pairings.

  • Contrast is a token-set constraint: content tokens meet WCAG AA against their intended surfaces — 4.5:1 body text, 3:1 large text and UI boundaries — in both schemes.
  • Meaning never rides on colour alone — pair every intent colour with text or an icon.
  • Stay in one family when placing text on a tinted background (danger text on danger-subtle, never on info-subtle).
  • Ration the accent. Links, focus, and the single primary action — not headings, borders, or decoration.

Spacing

A 4px base scale. Every margin, padding, and gap resolves to a step — the scale removes decisions, which is the point.

Where each band belongs

  • Proximity is hierarchy: related things sit one band closer than unrelated things. Spacing communicates grouping before a single border is drawn.

  • 12 columns when a grid is needed, gaps from the spacing scale — but most SaaS screens are a content column plus rails; don't force a grid where flow works.

Foundation

Shape & border

Four radius steps, each owning specific surfaces — rounder means bigger and more elevated.

--radius-1 badges, chips, checkboxes
--radius-2 buttons, inputs, selects
--radius-3 cards, dropdown panels
--radius-4 modals, sheets
--radius-roundavatars, pills

Concentric nesting

outer = inner + padding

When a rounded element sits inside another, the outer radius equals the inner radius plus the padding between them — corners stay parallel instead of pinching.

  • Borders are --border-1 () by default; --border-2 is reserved for selected states and emphasis.
  • Radius follows the scale by surface type — don't re-solve corner rounding per feature.

Foundation

Iconography

One library, three sizes, drawn to match the type they sit beside.

--icon-size-sm dense UI · 12–14px text
--icon-size-md default · body text
--icon-size-lg navigation · feature icons
  • One icon library per project — a consistent grid, stroke (~1.5px), and corner language; never mix sets. (Which library: the active stack pack or project decision, recorded once.)
  • Icons inherit the text colour of their label and centre-align to its first line; slight opacity (≈0.84) balances stroke weight against text.
  • Icon-only buttons need an established metaphor (trash, pencil, ×) and an accessible name; anything less keeps its label.
  • Get the layout right first, then add icons where a label earns extra recognition — icons are seasoning, and overuse reads as clutter.

Foundation

States & focus

Every interactive element answers in the same ladder, driven by tokens — shown here on an abstract control, because the ladder is the spec, not the button.

Restaccent
Hover+1 ramp step
Pressed+2 ramp steps
Focusring, always visible
Selectedsubtle fill + border
Disabledsubtle bg, muted text
  • The state ladder is arithmetic: hover is one ramp step stronger than rest, pressed is two — for any hue, both schemes. No per-component state colours.
  • Focus is one spec everywhere: a ring (--color-focus-ring) offset by , on :focus-visible. Never remove an outline without this replacement.
  • On touch, pressed carries the feedback — hover is a pointer affordance; the touch path never goes without a visible response.
  • Disabled is visible but inert — muted, not hidden; never conveyed by colour alone when the reason matters (pair with helper text).

Foundation

Content & tone

Interfaces speak like a competent colleague: plain, direct, human. Copy is part of the design system, not something typed at the end.

  • Sentence case everywhere except proper nouns — buttons, headings, labels; one convention, no mixing.
  • Actions are verb-first and specific: "Save changes", "Delete invoice", "Send invite" — never "OK", "Submit", or "Yes".
  • Plain language: short sentences, no jargon or idiom, front-load the point. If a sixth-grader can't parse it, rewrite it.
  • Never blame the user; no alarm punctuation, no ALL CAPS, no "invalid user error" voice.
  • All copy is centralized (i18n dictionaries or the strings module) — so it can be reviewed as one surface, in every language.

Beyond foundations

Where are the components?

Deliberately not here. Products differ too much for this template to pin a component inventory — so components stay flexible per app, built over the project's chosen headless foundation and organised by the atomic tiers in apps/frontend/CLAUDE.md → Component structure.

What is not flexible is what they're made of: every component consumes the semantic tokens, answers with the state ladder, wears the focus ring, respects the motion bands, and meets the accessibility floor. Two apps with different components should still be recognisably one practice.

Twice is a coincidence, thrice is a pattern.

When a component shape recurs across features, promote it into the app's shared atoms//molecules/; when it recurs across projects, consider adding its specimen to this guide so the next app starts with it. That is how this document grows — from evidence, not speculation.
