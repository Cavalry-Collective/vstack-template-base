Keystone · design guide

Many apps. One design philosophy.

The foundation for every product built from this template — the principles, tokens, and rules that make ten different apps feel like one practice built them. Components stay flexible per app; everything they're made of starts here.

Cavalry palette · token-driven · WCAG AA

  • New project? Rebrand the primitive tier of tokens.css; every page here re-derives. Confirm in a browser before building screens — that's the gate.
  • Building? Pick the screen archetype first; consume semantic tokens only.
  • Reviewing? Each chapter ends in checkable rules; a violation is the defect.

There are no special cases. If the scale can't express a need, extend the scale — never the screen. A one-off value is how a system dies.

Start

Principles

Six commitments, in priority order. When two collide, the earlier wins.

01

Clarity first

Hierarchy, not decoration, does the explaining. Strip everything non-essential.

02

No special cases

Every colour, size, space, and duration resolves to a token. Extend the system, never the screen.

03

One primary action

One filled, accent-coloured action per view. Everything else recedes.

04

Every state is designed

Loading, error, empty, success — first-class. Feedback lands on the control that caused it.

05

Accessible by default

AA contrast, keyboard-first, visible focus, meaning never by colour alone. A floor, not a feature.

06

Calm, but instant

Motion is short and purposeful; every interaction answers immediately.

Start

Tokens

One source, three tiers — small enough to hold in your head.

A design token is a design decision with a name. Instead of writing #e02b20 on a button, the button asks for --color-accent and the token answers. Name a decision once and every screen that asks gets the same answer; change the answer and every screen follows. That is the whole trick — screens hold no colour, size, space, or timing opinions of their own.

The tokens live in one file, tokens.css, arranged in three tiers:

Naming carries the system: a primitive says what a value is (--red-400, --space-3); a semantic token says what it's for (--color-accent, --page-title-gap). Screens speak only the role language — which is why a palette swap, or a future dark remap, never touches a screen. One lookup, end to end:

  • A hex code or px literal in a screen is the greppable violation.
  • Semantic names describe the job, never the look — a token named after its colour can't survive a rebrand.
  • One light theme. Dark, if ever needed, is a remap of the semantic tier only.

Foundation

Colour

The Cavalry palette: purple-cast neutrals, Cavalry red for action, violet / green / amber for meaning.

Roles — what screens use

Screens never name a hue. They ask for a role — accent, danger, border — and the role picks the step. The ramps further down are raw material for these roles; a screen that reaches past a role into a ramp is off-system (Tokens).

TokenValueUse for

Ramps — the raw material

Each hue is a small ramp of numbered steps; the roles above resolve into them. Hover a step for its value.

The intent formula: subtle background = 50 · border = 200 · interactive / content = 400 (holds ≥ 4.5:1 on white) · text-on-tint = 600. The interactive red adds hover = 500 and pressed = 600; the support hues carry no hover duty, so four steps is their whole ramp. Neutrals run six for surface, border, and text work. Brand-vivid values that can't hold 4.5:1 (--red-300 — the pure brand red — and --amber-400) are for graphics and large accents only, never body-size text on white.

  • Screens consume roles, never ramp steps — the ramp is the primitive tier behind the role (Tokens).
  • Content tokens meet AA against their surfaces — 4.5:1 body, 3:1 large/UI (every pairing verified).
  • Meaning never rides on colour alone; ration the accent to links, focus, and the one primary action.
  • Accent and danger share the brand-red family here — destructive actions are disambiguated by verb-first labels and confirmation, never hue.

Digits

Wrapping & truncation

Text wraps by default, and layouts assume it — no fixed-height text boxes. Truncation is a last resort for genuinely fixed slots (a table cell, a list-row title): one line, an ellipsis, and the full value reachable — a tooltip, or the row's detail view. Long unbroken strings (URLs, emails) break mid-string rather than stretch their container. Data values are the exception and never truncate or split (Data formatting).

  • UI text — buttons, badges, table headers, card values — is a full string set in medium; bolding a word inside a sentence is strong, a different thing.
  • ~4 sizes and 2 weights per screen; a new size is a new scale step, never a one-off.
  • Body measures ≤ --measure; one H1 per page, no skipped heading levels.
  • Wrap by default; ellipsis only in fixed slots with the full value reachable — never on headings, labels, or buttons.

Spacing

Six steps. Proximity is hierarchy — related things sit one step closer.

The box model

A container's inner padding is a box, not a spacing decision: three sizes, default in the middle, one size per column.

Vertical rhythm

  • 1–2 inside controls · 3 component gaps · 4 between components · 5 between sections · 6 page-level.
  • Page-level gaps have names — --page-title-gap, --page-section-gap — fixed by the screen archetype, never re-derived.
  • If the scale can't express a layout, fix the scale — not the instance.

Foundation

Layout

Three regions, two breakpoints, and a shared layout that owns the frame.

Anatomy

The shared layout component supplies regions 1 and 2 — the top bar and the nav rail — plus the screen gutters, and it alone reads the clearance tokens, so fixed chrome reserves its space exactly once, safe-areas included. Region 3 is the only region a page owns, and even there the page doesn't improvise: its shape comes from its screen archetype. Below sm the rail gives way to a menu — or a bottom bar when the project is mobile-first — and the same page fills the same body region unchanged.

Grid

Columns are percentages, so they breathe with the viewport; gutters hold at --space-3, so density stays even at any width. A block spans columns, never pixel widths — six of twelve is half the page everywhere. Two container widths cap the body: --container-content for working screens, --container-narrow for reading and focused flows; the archetype picks between them. Everything the frame owns has a token, and pages consume these through the layout without restating them:

TokenValueOwns
--breakpoint-smNav docks; fields go side-by-side; 8 columns
--breakpoint-lg12 columns, side panels
--side-nav-widthThe fixed nav rail
--container-contentStandard pages
--container-narrowReading, focused flows
--gutter-screenScreen edges — applied by the layout
--header-clearanceFixed-chrome space, safe-area included, counted once
  • Author from 320px up; no sideways scroll, ever.
  • Prefer intrinsic sizing (wrap, min/max, container-fit) to breakpoints; add one only for a real layout change.
  • Pages pick a layout variant; they never re-derive gutters or clearances.
  • The layout owns the frame; what fills the body region is the screen archetype's decision.

Content

Interfaces speak like a competent colleague: plain, direct, human.

  • Sentence case everywhere. Actions verb-first: "Save changes", never "OK".
  • Short sentences, no jargon, front-load the point. Never blame the user.
  • All copy centralized (i18n dictionaries / strings module) — reviewable as one surface.
  • One action, one verb — the vocabulary below; an action never ships under two labels.
SurfaceThe copy's job
EmptyWhy it's empty + the next step: "No invoices yet. Create your first invoice."
ErrorWhat happened + what to do, with the reference id. Never a dead end.
SuccessConfirm and name the object: "Invoice sent to Acme."
DestructiveName the consequence and count: "Delete 3 invoices? This can't be undone."

Composition

Screen archetypes

Seven page shapes cover the product. Name the archetype before you build — the page frame is a decision already made, so page five looks like page one.

One page, one archetype. A zone may host another archetype's content pattern (a dashboard widget shows a mini collection), but exactly one archetype owns the frame. No fit? Extend this set in the guide — never improvise a page shape on a screen.

The page skeleton

Every archetype starts from the same skeleton: a page header — one title (the page's only H1), with optional description, back link or breadcrumb, and page-level actions on the trailing edge — then that archetype's zones. The app frame around it (top bar, nav, gutters) belongs to Layout; archetypes shape what fills the body region.

TokenValueOwns
--page-title-gapPage header → first content
--page-section-gapBetween sections within a page

Edges and widths are the layout's: --gutter-screen, --container-content, --container-narrow (Layout).

Collection

Many records, one type — scan, narrow, act.

Record detail

One record's whole story: identity, key facts, then the detail.

Form

Create or edit in one sitting — one column, nothing competing for attention.

Dashboard

The product's pulse — read in seconds, then jump to the work.

Settings

Read and adjust in place — grouped, labelled, predictable.

Multi-step flow

One topic per step, 3–8 steps, a review before commit.

Full-page utility

Sign-in, not-found, full-page failure, first-run — the app frame steps aside.

Density

The box scale (Spacing) is the app's density: a denser product remaps --box-padding-* once, at the token layer. A zone's box size is part of its archetype — collection rows sit in box-sm by definition; that is the archetype speaking, not a per-page density choice.

  • Name the archetype before building any screen — its zones, gaps, and width are decisions already made.
  • Page rhythm is token-only: --page-title-gap under the header, --page-section-gap between sections, edges and widths from Layout. Never re-derived per page.
  • Exactly one archetype owns a page; zones may host other archetypes' content patterns.
  • No fit → extend this set in the guide first. A page shape invented on a screen is a one-off by definition.
  • One density app-wide, set at the token layer — never mixed within a page hierarchy.

Composition

Forms

Labels on top, one column, actions where the flow ends — whatever component library the app adopted.

Field anatomy

Validation & recovery

  • Label above the field, always visible; the placeholder is never the label.
  • Field width mirrors the expected answer; only short, related fields share a row (from sm).
  • Mark optional fields "(optional)" — nothing is asterisked.
  • Helper text sits under the input; the error replaces it, names the fix, and focus moves to the first failure on submit.
  • Fields sit --space-3 apart; groups --page-section-gap apart (Form archetype).
  • Actions close the form — primary on the trailing edge, secondary beside it, destructive apart on the leading edge. Same order in dialogs and inline.
  • The pattern outranks the library default: configure the library to match; what it can't express is justified via the reuse ladder.

View states & feedback

A state replaces only the zone it describes — the page keeps its frame. Feedback lands where the cause lives. The words: Content; this chapter decides placement.

Where states live

StateWhere it rendersShape
Loading, firstIn the zone it describesSkeleton mirroring that zone's skeleton
Loading, refreshStale content stays putSubtle indicator on the zone or control — never a page wipe
EmptyIn the zone, where records would beWhy it's empty + the next step
ErrorIn the zone that failedWhat happened + what to do, with retry
PartialLoaded zones renderSkeletons only where data is still due

Feedback routing

OutcomeRoute
A control's own result — validation, toggle, pressInline, at the control that caused it
Async action confirmed or failed after the factToast — transient, non-blocking, names the object
A decision blocks the action — destructive, unsaved changesDialog — names the consequence and count
System-wide condition — offline, expiring planBanner atop the affected zone or page
  • A state replaces only the zone it describes; the page frame never blinks out.
  • Known shape → skeleton mirroring the zone; unknown wait on an action → indicator on the control. Never both for one wait.
  • Refresh keeps stale content under a subtle indicator — no wipes, no layout jumps.
  • Route feedback by cause: inline → toast → dialog → banner, the lightest that fits; it always lands on (or names) what caused it.
  • Every state's copy follows the Content table — placement here, words there.

Beyond

Components & reuse

Reuse before invention — nothing new is built before the ladder below is exhausted.

Where are the components? Deliberately absent — apps differ too much to pin an inventory. What's fixed is what components are made of: semantic tokens, the state ladder, the focus ring, the motion bands, the accessibility floor. Two apps with different components should still read as one practice.

Before you build

Every new screen, section, or control starts by working down this ladder and stopping at the first rung that fits. "It already exists but I'd write it differently" is not a reason to descend.

The bar for new: demonstrably needed, and replicating nothing that already exists. A near-duplicate with different styling fails the bar — restyle or extend the original instead.

Twice is a coincidence, thrice is a pattern. Recurs across features → promote into the app's atoms/. Recurs across projects → earn a specimen here. The guide grows from evidence, not speculation.

  • Work the ladder before the editor: archetype → documented pattern → existing screens & primitives → extend a primitive → only then new.
  • New passes the bar — demonstrably needed, replicating nothing — and the PR records why nothing above fit.
  • Promotion stays evidence-driven: twice a coincidence, thrice a pattern.
