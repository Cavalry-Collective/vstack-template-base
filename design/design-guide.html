Keystone · design foundations

Many apps. One design philosophy.

The foundation for every product built from this template — the principles, tokens, and rules that make ten different apps feel like one practice built them. Foundations only: components stay flexible per app, but everything they're made of starts here.

Token-driven Light · minimal WCAG AA Foundations, not components
  • New project? Rebrand the primitive tier of tokens.css; this page re-derives. Confirm it in a browser before building screens — that's the gate.
  • Building? Consume semantic tokens only.
  • Reviewing? Each chapter ends in checkable rules; a violation is the defect.

There are no special cases. If the scale can't express a need, extend the scale — never the screen. A one-off value is how a system dies.

Start

Principles

Six commitments, in priority order. When two collide, the earlier wins.

01

Clarity first

Hierarchy, not decoration, does the explaining. Strip everything non-essential.

02

No special cases

Every colour, size, space, and duration resolves to a token. Extend the system, never the screen.

03

One primary action

One filled, accent-coloured action per view. Everything else recedes.

04

Every state is designed

Loading, error, empty, success — first-class. Feedback lands on the control that caused it.

05

Accessible by default

AA contrast, keyboard-first, visible focus, meaning never by colour alone. A floor, not a feature.

06

Calm, but instant

Motion is short and purposeful; every interaction answers immediately.

Foundation

Colour

One neutral, one accent, three intents — five steps each. Hover a step for its value.

The intent formula: subtle background = 50 · border = 200 · interactive = 400 · hover = 500 · active / text-on-tint = 600. A new intent is a new family plus this formula — nothing else.

TokenValueUse for
  • Content tokens meet AA against their surfaces — 4.5:1 body, 3:1 large/UI.
  • Meaning never rides on colour alone; ration the accent to links, focus, and the one primary action.

Spacing

Six steps. Proximity is hierarchy — related things sit one step closer.

  • 1–2 inside controls · 3 component padding · 4 between components · 5 between sections · 6 page-level.
  • If the scale can't express a layout, fix the scale — not the instance.

Foundation

Icons

One library, two sizes, coloured by their label.

--icon-size-sm inline with text
--icon-size-lg navigation, features
  • One icon set per project, recorded once — never mix. Icons inherit the label's colour.
  • Icon-only needs an established metaphor and an accessible name; otherwise keep the label. Icons are seasoning — layout first.

States & focus

One ladder for every interactive element — shown on an abstract control, because the ladder is the spec.

Rest400
Hover500 (+1)
Pressed600 (+2)
Focusring, visible
Selectedsubtle + border
Disabledmuted, not hidden
  • Hover = +1 step, pressed = +2 — arithmetic, not per-component colours.
  • Focus: --color-focus-ring ring, offset , on :focus-visible. Never removed without this replacement.
  • On touch, pressed carries the feedback — the touch path never goes silent.

Foundation

Accessibility

The floor, carried by the tokens. Full checkable baseline: apps/frontend/CLAUDE.md.

  • AA contrast in the semantic pairings · visible focus via the ring tokens · reduced motion at the token layer.
  • Reflow at 320px, usable at 200% zoom · touch targets ≥ .
  • Meaning never by colour alone · heading outline = document structure.

Foundation

Content

Interfaces speak like a competent colleague: plain, direct, human.

  • Sentence case everywhere. Actions verb-first: "Save changes", never "OK".
  • Short sentences, no jargon, front-load the point. Never blame the user.
  • All copy centralized (i18n dictionaries / strings module) — reviewable as one surface.
SurfaceThe copy's job
EmptyWhy it's empty + the next step: "No invoices yet. Create your first invoice."
ErrorWhat happened + what to do, with the reference id. Never a dead end.
SuccessConfirm and name the object: "Invoice sent to Acme."
DestructiveName the consequence and count: "Delete 3 invoices? This can't be undone."

Beyond

Where are the components?

Deliberately absent — apps differ too much to pin an inventory. What's fixed is what components are made of: semantic tokens, the state ladder, the focus ring, the motion bands, the accessibility floor. Two apps with different components should still read as one practice.

Twice is a coincidence, thrice is a pattern. Recurs across features → promote into the app's atoms/. Recurs across projects → earn a specimen here. The guide grows from evidence, not speculation.
